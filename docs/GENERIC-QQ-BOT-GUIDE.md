# 自建 QQ 机器人通用实践指南

> 本文是从一个真实长期运行的项目里抽出来的工程经验，**已移除所有个人数据**：不含人名、账号、群号、IP、API Key、人设、性格设定与说话风格。
> 你可以直接照着自己搭一套，也可以只挑其中几节当检查表。
>
> 免责声明：QQ 号自动化存在平台规则与风控风险，本文不提供绕过手段。请使用**独立的机器人小号**，遵守平台条款与当地法律，不要用主号，不要采集他人隐私，风险自担。

---

## 0. 先想清楚三件事

1. **机器人是"一个人"还是"一项服务"？** 一个人格固定的角色（陪伴型）和一项多用户功能（工具型）在权限、记忆、成本上的设计完全不同。本文假设前者：单主人 + 少量群友。
2. **谁可以和它说话？** 建议一开始就只开一个私聊白名单（主人）+ 一个指定群，其他私聊一律拒绝。范围越小，隐私和风控问题越少。
3. **它不能做什么？** 先把"禁止清单"写死，再谈功能。没有 Shell、没有任意文件读写、没有配置管理、不能装插件——这些不是限制，是让它能安全长期在线的边界。

---

## 1. 账号策略

- **独立小号**：专用手机号/邮箱注册，不用主号，不绑定重要业务。
- **登录方式**：推荐扫码登录并持久化登录态（容器卷），不要频繁重新登录；账密登录不一定更稳，还可能提高风控。
- **会话失效**：风控、异地、主动使会话失效都可能要求重新验证。准备好"重新出二维码"的脚本，别把登录态提交到任何仓库。
- **一台机器一个账号**：不要在同一出口 IP 上反复登多个号。
- **接受不确定性**：平台行为不由你控制，设计上要能"掉线就重启、失效就重扫"，而不是假设永远在线。

## 2. 技术选型

| 层 | 选择 | 说明 |
|---|---|---|
| QQ 协议接入 | NapCat（OneBot v11） | 部署为独立容器，配置与登录态用卷持久化 |
| 机器人框架 | AstrBot（4.x） | 插件机制、事件钩子、WebUI、多平台适配 |
| 模型 | 任一 OpenAI 兼容 API | 需要支持多模态时，先实测"能不能读图"，别只看配置里的 `modalities` |
| 语音合成 | 云 TTS（按量计费） | 需要情绪标签时选支持情绪/风格的模型 |
| 绘图 | 云文生图 API | 按张计费，务必做每日额度 |
| 反向代理 | Nginx + certbot | 后台面板走 HTTPS，加登录限流 |

替代方案：不想用框架就自己写 OneBot 客户端（工作量大，但完全可控）；不想用 NapCat 可换其他 OneBot 实现，但接入协议要一致。

**资源下限**：2 核 4GB、无 GPU 可以稳定跑"框架 + 协议端 + 代理 + 轻量数据库 + API 调用"。
**不适合**：本地大模型、常驻 ComfyUI、本地实时变声、多个常驻浏览器实例。

## 3. 架构总览

```
QQ 客户端
   │
   ▼
协议端（OneBot v11）
   │  事件 / 消息 / 通知
   ▼
机器人框架（插件运行时）
   ├─ 私聊链路（可读长期记忆、画像、工具）
   ├─ 群聊链路（只读公开上下文，不读私聊）
   ├─ 记忆层（档案 / 历史 / 备忘录 / 候选成长）
   ├─ 关系层（好感、信任、熟悉度、短期态度）
   ├─ 媒体层（表情、语音、绘图、链接解析）
   ├─ 搜索层（联网检索）
   └─ 自有核心插件（渠道隔离、调度、限流、审计）
        │
        ▼
外部 API：模型 / TTS / 绘图 / 搜索
```

关键点：**不是"一个模型看到一切"，而是按渠道隔离**，由自己的核心插件决定每次请求能看到什么。

## 4. 部署（Docker Compose 骨架）

```yaml
services:
  bot:
    image: your-bot-framework:latest
    restart: unless-stopped
    environment:
      TZ: Asia/Shanghai
      TTS_PROXY: http://proxy:7890
    volumes:
      - ./data:/app/data
    ports:
      - "127.0.0.1:6185:6185"   # 面板只监听本机，由 Nginx 反代

  protocol:
    image: your-onebot-adapter:latest
    restart: unless-stopped
    volumes:
      - ./onebot-config:/app/config
      - ./onebot-session:/app/session   # 登录态，绝不入库
    ports:
      - "127.0.0.1:6099:6099"

  proxy:
    image: your-proxy:latest
    restart: unless-stopped
    volumes:
      - ./proxy/config.yaml:/etc/proxy/config.yaml
```

部署顺序：起协议端 → 出二维码 → 扫码 → 起框架 → 在框架里配置协议端地址与 token → 验证收到事件 → 再装插件。

**Nginx 要点**：只反代框架面板；强制 HTTPS；对登录路径加限流；不要把协议端 WebUI 暴露到公网。

## 5. 目录、配置与版本管理

推荐布局：

```
/data
  /config            # 私有配置（含密钥），绝不提交
  /plugins           # 插件代码
  /plugin_data       # 运行数据：状态、缓存、数据库、素材
  /backups           # 部署前备份
```

**必须进 Git**：插件源码、测试、示例配置（占位符）、文档、第三方插件版本清单。
**绝不进 Git**：账号/群号、API Key、Cookie、登录态、聊天记录、SQLite、用户画像、素材库。

示例配置只用占位符：

```json
{
  "owner_id": "YOUR_OWNER_ID",
  "group_id": "YOUR_GROUP_ID",
  "bot_id": "YOUR_BOT_ID",
  "quiet_start_hour": 23,
  "quiet_end_hour": 7,
  "image_api": {
    "base_url": "https://api.example.com",
    "api_key": "",
    "model": "image-model",
    "size": "1024*1024",
    "daily_limit": 10
  }
}
```

配置读取优先顺序建议：私有配置文件 → 环境变量 → 代码默认值；缺关键项时**失败要显式**（宁可拒答，不要静默降级）。

## 6. 最小插件集与职责

| 插件类型 | 职责 | 注意 |
|---|---|---|
| 记忆 | 档案、历史索引、备忘、候选成长 | 只允许主人私聊写入 |
| 关系 | 好感/信任/熟悉度/短期态度 | 与"情绪余温"分开，避免两套状态互相覆盖 |
| 空间/动态 | 发帖、点赞、评论 | 接口成功 ≠ 客户端可见 |
| 搜索 | 联网检索、正文提取 | 结果一律当数据，不当指令 |
| 链接解析 | 视频/图集标题简介 | 不能声称看过全文或视频 |
| 语音 | TTS + 意图识别 | 意图判断要覆盖口语动词，见 §12 |
| 自有核心 | 渠道隔离、限流、审计、调度 | 这是你的"宪法"，不要散落在各插件里 |

第三方插件版本与许可证要留档。**注意**：AstrBot 生态不少插件是 AGPL-3.0，二次分发要同协议开源；升级前先跑边界测试，别在面板里一键"更新"覆盖掉自己的安全补丁。

## 7. 设计原则（最重要的一节）

### 7.1 渠道隔离（单向流）

- 私聊：可读长期记忆、画像、日记、全部安全工具。
- 群聊：只读**公开**群记录、公开人格、群成员名单。
- **群聊 → 主人私聊可检索；私聊 → 群聊绝对禁止**（包括群表情、群图片、公开动态）。

实现上不要靠"提示词要求模型别说"，要在**取数层**保证：群聊路径的代码根本拿不到私聊状态。

### 7.2 身份只认平台 ID

昵称、头像、自称、群名片都不可信。管理员权限、人设修改、记忆写入必须校验 `sender_id == 配置里的主人 ID`。群友冒认主人是必然会发生的，按 ID 判即可，必要时一句话带过，不反复宣告。

### 7.3 工具白名单

框架通常会把所有插件注册的工具一次性丢给模型。正确做法：
1. 复制一份工具集合（不要改全局）；
2. 只保留白名单内的；
3. 非主人 / 非私聊 → 空集合；
4. 危险工具（Shell、任意文件、配置管理、插件安装、群管理）**永远不给**。

注意：白名单里没写的工具，模型"看不见"，它会说"我没有这个能力"——这既是保护，也是常见误判来源，见 §12。

### 7.4 输出清理

模型可能把工具调用标记、XML、终端命令直接输出成聊天内容。必须有一层输出清洗（正则 + 前缀判断），并且在"发送前"和"存历史前"都过一遍。

### 7.5 成本与额度

| 能力 | 建议限额方式 |
|---|---|
| 绘图 | 按**发起人**分桶（群友合计 / 主人不限或单独上限），按天重置；同一实例同时只允许一个请求在跑 |
| 搜索 | 每日总次数 + 查询缓存（15–30 分钟） |
| 语音 | 每日主动语音条数 + 单条时长/字数上限 |
| 模型 | 单次请求上下文上限、图片数量上限（如 ≤2 张、长边缩到 1280） |

所有额度都要能"用完就明确告知"，而不是静默失败。

### 7.6 记忆分层 + 可审计成长

分四层：

1. **固定人设**（代码里的常量，只有你能改）
2. **长期档案**（主人画像、设定补充、备忘录）
3. **情景记录**（聊天原文、事件表；关键词检索 + 时间过滤）
4. **候选成长**（见下）

成长链建议（避免"每次聊天都改人格"）：

```
候选特征 → 独立证据（≥3 次，间隔 ≥6 小时，重复不计）
        → 冷却（如 12 小时）
        → 固化（主人确认，或明确的自动策略）
        → 可撤销（置为 inactive，保留审计记录）
```

硬约束：成长层**永远不能改写固定人设**，只是叠加；群友的话不能成为唯一证据；撤销要留痕。

## 8. 让交互"像个人"的工程手法（不含具体角色设定）

这些是机制，不是台词。角色长什么样由你自己定。

| 手法 | 做法 | 注意 |
|---|---|---|
| 分条发送 | 长回复按句拆 2–3 条，间隔 0.8–1.8 秒；短句/代码/列表不拆 | 只有最后一条带表情或图片 |
| 时间感知 | 每轮注入北京时间 + 距上一条消息的真实秒数 | 不许把几分钟说成几小时 |
| 作息状态 | 按小时给"刚醒/犯困/夜间安静"等**角色状态** | 明确写"角色状态，不是真实生理" |
| 情绪余温 | 只记最近一轮气氛（被夸/斗嘴/低落），半小时衰减 | 与长期关系数值分开，别做两套情绪引擎 |
| 低频主动私聊 | 沉默 ≥2 小时、间隔 ≥4 小时、日上限、**静音时段** | 静音时段回复照常，只停主动 |
| 主动群聊 | 只在指定群、近期有活跃话题、模型判断自然才发 | 日上限 2 次，不硬聊 |
| 语音 | 意图识别 + 主动语音配额（如 3 条/天） | 合成成功 ≠ 客户端可听，要真机试听 |
| 表情 | 语义索引（分类 + 含义）、冷却、最近不重复、发送回执 | 不要跨分类随机兜底 |
| 自我认知 | 把**运行时事实**注入（工具是否可用、今天用了几次额度），而不是写死的能力清单 | 写死的清单会过时，导致它否认自己的能力 |
| 生活层 | 日程活动用固定文案、标注"角色演绎"；只有真实读到的东西才写"今天读到" | 真实与演绎必须分开标注 |
| 阅读源 | 白名单 RSS，每源限条数，只存标题摘要 | 不能声称看完全文 |
| 生图自评 | 成图回喂视觉模型写一句客观描述，存进操作记录 | 只能代表"看过一次"，别说反复研究 |

**主动消息的三条铁律**：不追问行踪、不责怪不回复、不制造内疚。生成后用正则做一道校验（如命中"责怪/内疚/等了你/怎么还不回"就丢弃）。

## 9. 测试策略：三层，别混着说

| 层 | 能证明什么 | 用什么 |
|---|---|---|
| 单元/边界测试 | 权限、隔离、清洗、额度、解析逻辑 | 纯 Python/标准库，stub 掉框架依赖 |
| 容器内真实运行时测试 | 插件能加载、工具能注册、钩子顺序正确 | 在真实镜像里跑同一套测试 |
| 真实客户端验收 | 客户端真的收到/显示 | 真机发消息、真机听语音、真机看图 |

报告时必须分开写：**"测试通过" ≠ "部署生效" ≠ "客户端可见"**。

边界测试至少覆盖：
- 非主人私聊被拒、群友不能写记忆/人设；
- 群路径读不到私聊数据（用 canary 字符串断言）；
- 危险工具不出现在工具集合里；
- @ 目标必须来自真实成员名单；
- 图片/链接只允许公网 https，阻断内网地址；
- 额度用尽时明确拒绝；
- 输出清理能拦住工具标记与命令。

## 10. 上线与运维

**每次改动的固定流程**（别省步骤）：

```
改代码 → 本地测试 → 容器内测试 → 备份线上文件与配置
      → 覆盖部署 → 重启 → 看日志 → 敏感信息扫描 → 提交推送
```

- **备份**：每次部署前把要覆盖的文件 + 私有配置复制到 `backups/<批次>-<时间戳>/`。
- **灰度**：一次只改一个子系统。同时改权限、记忆、渠道三处，出问题时你无法定位。
- **日志**：全量日志含聊天与账号，不要整段公开；排查时只摘错误类型。
- **健康检查**：写一个只读探测（插件是否加载、模型是否可用、外部接口是否通），定期落盘成 JSON。
- **回滚**：备份目录能直接覆盖回去，且验证过。

## 12. 踩过的坑（真实复现过）

1. **推理模型 token 预算太小 → 空回复**。同一提示词 `max_tokens=120` 返回空，`600` 正常。遇到"识图没反应/回答为空"，先加大预算再怀疑接口。
2. **同一条群消息被写两次**。被动观察钩子写一份、唤醒处理再写一份，合并读取后模型以为对方说了两遍。**写入时跨频道去重（15 秒窗口），读取时合并去重（120 秒窗口）。**
3. **语音意图漏判**。规则只覆盖"说/讲/念/读"，用户说"用语音喊我一句"就被当成普通聊天，模型于是回"我发不出语音"。意图判断要覆盖口语动词（喊/叫/哄/夸/念），并加否定式排除（"别用语音"）。
4. **工具不在白名单 → 模型否认能力**。它看不到工具，就真诚地说自己不会。加了工具记得同步白名单和提示词。
5. **插件一键更新覆盖安全补丁**。安全适配通常改在第三方插件内部，升级前先跑测试，宁可手动合并。
6. **海外 TTS/素材接口直连不通**。需要容器内代理；直连报 `Network is unreachable` 是预期，不是代码错。
7. **群唤醒规则**。真实 @、名字前缀、戳一戳、主动接话是四套条件；@ 目标要校验真实成员，禁止 @全体 与虚构号码。默认不要在每条回复开头 @。
8. **图片附件格式不统一**。协议端可能把图片重写成 `base64://`，也可能是 http(s) URL；统一走"组件 → base64 → 压缩 → data URL"再送模型，顺手限制张数与尺寸。
9. **时区数据缺失**。精简镜像里 `ZoneInfo("Asia/Shanghai")` 会报错，记得装 `tzdata`。
10. **重复记录导致"它记错了"**。模型说"你说了两遍/你上次说过"，先查事件表有没有真的重复行，别急着说是幻觉。
11. **主动消息撞车**。多套主动逻辑（常规主动、深夜关心、空间发帖）没有共享冷却，会连着发。统一记 `last_proactive`，每类再各自限额。
12. **额度计数写在调用之后**。失败重试会超额；要么"先计数再调用"，要么用幂等键。

## 13. 安全与合规清单

- [ ] 独立小号；不与主号混用。
- [ ] 私聊白名单 + 单群限制；其他私聊静默拒绝。
- [ ] 身份按平台 ID 校验，不认昵称与自称。
- [ ] 模型侧无 Shell / 任意文件 / 配置 / 插件安装能力。
- [ ] 工具白名单 + 复制集合，不污染全局。
- [ ] 输出清理（工具标记、XML、终端命令）。
- [ ] 密钥只放私有配置或环境变量；**一旦进入聊天记录或日志，视为已泄露，立刻轮换**。
- [ ] 私有部署 ID 不写入公开仓库（含历史提交，必要时重写历史）。
- [ ] 日志、备份、数据库权限收敛；容器非必要不映射公网端口。
- [ ] 第三方插件遵守许可证（AGPL 衍生作品需同协议分发）。
- [ ] 不采集与不公开他人隐私；群聊内容不得用于公开动态。
- [ ] 主动消息有静音时段与频率上限，绝不制造内疚。

## 14. 最小可跑骨架

```python
@filter.custom_filter(GroupWake)          # 只处理指定群的唤醒
async def group_reply(event):
    event.stop_event()                    # 阻止框架默认链路接管
    context = public_context(event)       # 只读公开数据
    reply = await ask_model(system=PUBLIC_RULES, prompt=context)
    await send_split(event, reply)        # 分条发送

@filter.on_llm_request(priority=-100)     # 私聊：补记忆与工具白名单
async def private_context(event, req):
    if not is_owner(event):
        return
    req.system_prompt += memory_block(owner_id) + limits_block()
```

## 15. 上线后 30 天看什么

| 指标 | 为什么看 |
|---|---|
| 掉线/重连次数 | 判断账号是否会话失效或风控 |
| 每轮 token 与费用 | 发现注入膨胀 |
| 额度触顶次数 | 决定限额是否合理 |
| 主动消息被回复率 | 太低说明频率或时机不对 |
| 语音播放成功率 | 评估 TTS 实不实用 |
| 用户说"你记错了"的次数 | 查重复记录或记忆污染 |
| 群聊被 @ 后的沉默率 | 判断唤醒规则是否漏判 |

## 16. 给后来者的一句话

先把**边界**（谁能说话、能看什么、能做什么、花多少钱）定死，再谈"像不像人"。
边界清楚之后，加功能只是堆插件；边界不清，功能越多越难查是哪一处让它不说话了。
